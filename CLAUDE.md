# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo is a FastAPI backend + Next.js frontend for triggering and reviewing SAST scans (repo discovery plus LLM-driven findings), plus CI integration docs. This file only covers `backend/` and `frontend/` — the repo root also has scratch/debug artifacts (scan output JSON/txt/err dumps, PDFs) that aren't part of the project structure.

## Commands

### Backend (`backend/`)

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Run tests:

```bash
pytest                          # all tests (pytest.ini sets pythonpath=. from backend/)
pytest tests/test_scans_api.py  # single file
pytest tests/test_scans_api.py -k test_name   # single test
```

Tests default to the **mock engine** (`USE_MOCK_ENGINE=true` is not required — `app/config.py`'s `use_mock_engine` default is only overridden by the `USE_MOCK_ENGINE` env var), so the suite never touches git, the network, or AWS/Bedrock.

### Frontend (`frontend/`)

```bash
npm install
npm run dev      # next dev --webpack
npm run build    # next build --webpack
npm run lint     # eslint
```

There is no frontend test runner configured (no jest/vitest in `package.json`) — only `lint` and the Next.js build.

## Architecture

### Split responsibilities

- **`backend/app/`** — FastAPI app: `routers/` (HTTP), `services/` (scan lifecycle, git checkout, engine bridge), `models.py`/`schemas.py` (SQLAlchemy + Pydantic), `db.py` (engine/session setup + manual migrations).
- **`backend/sast_engine/`** — a separate, only-loosely-coupled LangGraph agent (see below). Not a normal Python package under `app/` — it's dynamically loaded by path.
- **`frontend/`** — Next.js App Router. `app/api/**/route.ts` are server-only proxy routes that forward the signed-in user's session (via `lib/server-sast.ts`'s `sastFetch`, see **Auth** below) to the FastAPI backend; client components call those routes through `lib/api.ts`, never the FastAPI backend directly. `frontend/AGENTS.md` (pulled in via `frontend/CLAUDE.md`) warns that this Next.js version has breaking API changes vs. training data — check `node_modules/next/dist/docs/` before writing Next-specific code.
- **`frontend/app/dast/**`** is a UI-only mockup (`lib/dastMockData.ts`) with no backend behind it — don't treat it as wired up to `backend/`.

### Scan engine: mock vs. real, and the discovery + findings pipeline

`backend/app/services/engine_adapter.py` is the single gate between the two engine paths, controlled by two independent flags in `app/config.py`:

- `USE_MOCK_ENGINE` (default true in tests) — returns deterministic fake discovery output, no I/O.
- `RUN_LIVE_SAST` — explicit opt-in required on top of `USE_MOCK_ENGINE=false` before the real engine runs at all.

The real engine maps a repo's structure, tech stack, and file-level risk, **then runs LLM-driven vulnerability detection and writes `Finding` rows** — it is no longer discovery-only (that was a temporary simplification; findings came back via the "Add CRITICAL-file LLM findings scan" commit onward, this time via LLM calls rather than the old AST/semgrep-based detection). Its 9 LangGraph nodes (`backend/sast_engine/sast_scan_agent.py`):

```
node_scan_directory -> node_analyze_tech_stack -> node_categorize_files -> node_map_modules_and_risk
  -> node_scan_deep_files -> node_scan_triage_files -> node_group_triage_findings
  -> node_confirm_triage_groups -> node_generate_report
```

- **Tech-stack detection** (`node_analyze_tech_stack`) is fully deterministic (no LLM call) — marker-file heuristics, dependency-manifest parsing (`pipeline/dependency_scan.py` + `pipeline/manifest_parsers.py` + `pipeline/stack_signatures.py`), and a tree-sitter AST pass (`ast_struct.py`, Java/Angular only). It also logs which **vulnerability surfaces** the detected stack activates (see below).
- **`node_scan_deep_files`** sends the **top `DEEP_SCAN_FILE_CAP` (100) CRITICAL/HIGH files, by priority** (CRITICAL first then HIGH; once the call graph exists, `_rank_deep_scan_by_attack_surface` re-picks the set from every CRITICAL/HIGH candidate by framework entry points then typed sinks per file — `call_graph.attack_surface_counts` — moving files that lose a slot to the front of triage; overridable via `state["deep_scan_file_cap"]`) to the LLM in full (`pipeline/llm_file_scan.py`), using the rule catalog as prompt guidance rather than a gate; findings are written incrementally with `kind=llm`. This tier also owns the *absence* checks a regex can't express (missing `@PreAuthorize`, unset `HttpOnly`, no CSRF token) — only files that make it into this tier get that coverage. The base system prompt (`llm_file_scan._SYSTEM_HEAD`) names the sink classes the model should actively hunt for; a comparison against GitLab's taint-flow SAST on the same repo found real reflected-XSS-via-HTTP-response-body and log-injection findings ours missed because `_SYSTEM_HEAD` only said "the DOM" (read as client-side) with no mention of a backend echoing exception/validation text into a response body, a log call, or CSRF misconfiguration — all three are now named explicitly. A second gap comparison, this time against a different SAST tool's report on the same repo, found the response-body/log-injection wording was still too implicit for three specific idioms — a raw `@RequestParam`/`@PathVariable` value echoed back (not just an exception message), a message first assigned to a local variable rather than passed inline, and integer underflow (CWE-191, an unchecked decrement/subtraction feeding an index/bound/size without a prior check) — none of which had ever been named at all; all three are now explicit in `_SYSTEM_HEAD` (`integer-underflow-llm-only` documents the underflow case in `scan_limitations.py` as LLM-only, since it can't be expressed as a regex without a high false-positive rate). Checking that second comparison's actual target-repo source (not just its report) surfaced two further, genuinely generic bugs in the regex fixes rather than repo-specific gaps: `java-log-injection-unsanitized-input`'s `[^)]*` prefix couldn't cross the closing paren of an *earlier* sibling argument in a multi-arg parameterized log call (e.g. `log.warn("{} {}", request.getRequestURI(), ex.getMessage())` — extremely common real-world SLF4J style) to reach `.getMessage()` later in the same call, and it never recognized `request.getRequestURI()`/`getRequestURL()`/`getQueryString()` as sources at all (only `getParameter`/`getHeader`) — both fixed by switching the prefix from `[^)]*` to a bounded `[\s\S]{0,200}?` and adding the missing accessors. `spring-exception-message-in-response-body` never recognized the `new ResponseEntity<>(dto, status)` constructor form at all — only `.body()`/`.ok()` — even though a DTO built via `.message(ex.getMessage())`/`.setMessage(fieldError.getDefaultMessage())` and returned via `new ResponseEntity<>(...)` is the single most common `@ExceptionHandler` idiom; fixed with a third alternative matching the DTO setter call directly, independent of how the DTO is later returned. `STACK_PROFILES["maven-java"]["rules"]` also gained a filename-based rule for `*SecurityConfig*`/`*WebSecurityConfig*`/`*SecurityFilterChain*.java` (CRITICAL, regardless of package) — the standard Spring Boot naming convention for the CSRF/CORS/authorization bean, which previously only reached CRITICAL if it happened to sit in a `security`/`auth` directory, exactly the same class of miss the `ExceptionHandler`/`ControllerAdvice` filename rule fixed above. **When CRITICAL/HIGH doesn't fill the cap, `node_map_modules_and_risk` backfills the leftover slots with the highest-priority MEDIUM (then LOW) files** (`state["backfill_deep_scan"]`, default on; CLI-only opt-out via `--no-backfill-deep-scan`, same as `deep_scan_file_cap`/`triage_batch_size`/`group_triage_mode` — never threaded through `agent_bridge.py`) rather than leaving that LLM budget unused — a real scan with a small CRITICAL/HIGH bucket (37 of 100 slots) used to send zero MEDIUM/LOW files through the full LLM pass regardless of the 63 spare slots. Backfilled files keep their true MEDIUM/LOW `risk_level` for reporting (`risk_counts` is computed before tier-routing runs and never reads `deep_scan_paths` membership) — only *which tier scans them* changes, mirroring how CRITICAL/HIGH overflow already keeps its true risk_level when routed the other direction.
- **Risk classification also peeks at Java content** (`_java_content_risk`, first 16 KB): EJB home/remote/local interfaces drop to LOW, and JAX-RS resources, `@RestController`s, `@WebService` endpoints, servlets and `*Filter.java` servlet filters rise to CRITICAL wherever they live; `web.xml` is CRITICAL and Angular `environment*.ts` MEDIUM. **Test code** (`llm_file_scan.is_test_path`: test directories *and* names like `FooTest.java`, `FooIT.java`, `FooTestClient.java`, `*.spec.ts`, `test_*.py`) leaves both tiers (`module_plan.files_skipped_test`); both call graphs use the same function.
- **Risk classification is filename-aware, not just directory-aware, for one Java case**: `STACK_PROFILES["maven-java"]["rules"]` (`sast_scan_agent.py`) classifies `*ExceptionHandler*.java`/`*ControllerAdvice*.java` as HIGH regardless of package, alongside the directory-based controller/service/repository/security rules. Without this, a `GlobalExceptionHandler.java` living under `config/` (a real, structurally-natural place for one) fell through to the generic `src/main/java/` → MEDIUM fallback and was never reviewed by anything — no regex rule could match its `ResponseEntity`/exception-message idioms either, so it was invisible to both tiers.
- **`node_scan_triage_files`** handles whatever MEDIUM/LOW files the deep-scan backfill above didn't claim, **and** any CRITICAL/HIGH file past the cap (still counted as CRITICAL/HIGH in `risk_counts`, just routed here for scanning). It is **regex-only by default and makes no LLM calls at all**, for API scans too: the `triage-mode-llm-confirm` and `deep-scan-critical-only` limitations both default **off** (on a legacy Java repo they left 93 of 100 deep-scan slots idle and spent the $2 cutoff on per-file triage a third of the way through, while the group sweep resolved 1,084 findings in 69 groups). A file with zero hits is skipped entirely (no DB write), and every hit in a file that matches is written verbatim as a `kind=regex` finding with **`verdict="unverified"`** — a pattern matched, nobody reviewed it. This is a mode toggle, not a hard-coding: `state["triage_mode"]` / `--triage-mode` accepts `regex_only` (`DEFAULT_TRIAGE_MODE`) or `llm_triage`, which restores the older behaviour of sending hits plus a ±10-line window each to the LLM for a TP/FP ruling (`_hit_matches_finding` drops anything the model invents outside those candidates); repeats of one construct in a file are asked about once (`group_triage_candidates`: occurrence count + first `TRIAGE_GROUP_WINDOWS` excerpts) and the verdict applied to every occurrence. Batches (one per real module, else `state["triage_batch_size"]` slices) are progress reporting only: every file goes to one worker pool, and each batch logs its "done" line when its last file finishes (`on_file_done`). Past `regex_scan.PROCESS_POOL_MIN_FILES` (500) files the regex pass runs in `spawn`-started worker processes (`scan_files_in_processes`; `state["triage_regex_processes"]` forces it either way), falling back to in-process with identical findings. MEDIUM is the largest tier in most repos (~2700 files on the target legacy Java repo), which is why it's regex-only: the local pass costs seconds where per-file LLM round-trips cost hours. The tradeoff is that catalog coverage bounds both recall *and* precision here, since nothing downstream filters a noisy rule.
- **`node_group_triage_findings`** runs after `node_scan_triage_files` (only when `triage_mode` is `regex_only`, gated by `state["group_triage_mode"]` / `--no-group-triage`, default on): groups that tier's `unverified` findings by construct — `llm_file_scan.group_key_for_finding` (`rule_id` + normalized `matched_text`), deliberately mirroring `scan_export._finding_group_key`'s regex branch so this collapses exactly what the UI already collapses into one row — and logs the resulting group/occurrence counts. **It makes no LLM call and leaves every finding's verdict as `unverified`** — this is grouping-only, so the collapse can be reviewed before deciding how to spend LLM tokens confirming TP/FP.
- **`node_confirm_triage_groups`** runs immediately after, gated by `state["confirm_triage_groups"]` (a no-op when falsy). The **CLI** (`sast_scan_agent.py`) defaults this off — opt in with `--confirm-triage-groups` for local debugging, where it also defaults to the top-`TRIAGE_CONFIRM_GROUP_CAP`(=50)-by-occurrence cap via `state["triage_confirm_group_cap"]`. **Real scans always turn it on and uncap it**: `agent_bridge.run_real_scan` sets `initial_state["confirm_triage_groups"] = use_llm` and `initial_state["triage_confirm_group_cap"] = None` unconditionally, so any API-triggered scan that has LLM scanning enabled at all confirms *every* unverified group — a scan should never finish with findings still sitting at `unverified` (short of a genuine, doubly-failed LLM call — see below). Both this node and `node_group_triage_findings` call `group_unverified_findings`/`group_confirm_unverified_findings` with their default `severities` — `llm_file_scan.UNVERIFIED_FINDING_SEVERITIES` (`LLM_RISK_LEVELS | TRIAGE_RISK_LEVELS`, i.e. every severity, not just MEDIUM/LOW). This default used to be `{MEDIUM, LOW}` only, which silently excluded CRITICAL/HIGH files that overflowed `DEEP_SCAN_FILE_CAP` into this tier — those findings kept their true CRITICAL/HIGH `risk_level`, so they never entered any group and sat at `unverified` forever regardless of the confirm step being on and uncapped. Fixed by widening the default rather than special-casing overflow severities at each call site. `groups_per_call` (`state["triage_confirm_groups_per_call"]`, default `DEFAULT_GROUPS_PER_CALL`=5) packs multiple groups into one LLM call via `confirm_finding_group_batch`, so the shared system-prompt/OWASP-label overhead is paid once per batch instead of once per group — the main token-reduction lever over the naive one-call-per-group approach; `LLM_COST_CUTOFF_USD` remains the real spend backstop now that there's no group cap. A batch call that fails outright, or a response that decides no member of some group (`group_index`), does **not** leave those groups `unverified` — `confirm_finding_group_batch` falls back to an individual `confirm_finding_group` call (itself with its own JSON-retry) for any group the batch didn't answer, and a follow-up call for the members of a partly answered one (see **Per-occurrence decisions** for how members are decided); only a group whose fallback call *also* fails ends up `unverified` with `error` set. Confirmed verdicts are persisted via `state["verdict_updates_writer"]` / `scan_runner._make_verdict_updates_writer` (an `UPDATE` keyed on `(scan_id, file_path, rule_id, line)` rather than a duplicate insert) — since `node_confirm_triage_groups` mutates the same `triage_scan_results["files"]` list `node_generate_report` reads next, the final report's true/false/unverified tallies reflect confirmed verdicts automatically, with no separate reporting-side change needed. See **LLM token efficiency** below for prompt caching and cross-scan result reuse on top of this batching.
- Files whose first 4000 chars carry a generated-code marker (`@Generated`, `DO NOT EDIT`, "automatically generated", Castor/JAXB banners — `llm_file_scan.looks_generated`) are skipped by **both** scan tiers and counted separately (`files_skipped_generated`). Detection is by **content, not path**, so hand-written files in a `castorgen/` directory are still scanned.
- **Declaration-only files** (`llm_file_scan.looks_declaration_only`) drop to LOW at risk mapping and are skipped by the deep scan. These are Spring Data repository interfaces with only derived query methods (no `@Query`/native query, `@RepositoryRestResource` or default methods) and `.ts` files holding only imports and `interface`/`type`/`enum` declarations. The demotion happens in `_java_content_risk`/`_ts_content_risk`, only when the whole file fits in the 16 KB peek. The regex tier still sees them, and the call graph still parses every Java file, so repository methods stay sinks. A real scan spent 28 of 100 deep-scan slots on such files, all "No findings".
- Vendored/minified third-party assets (jQuery, Bootstrap, ...) are skipped the same way, via `llm_file_scan.looks_vendored_or_minified`: filename ending in `.min.js`/`.min.css`, or content whose average line length is characteristic of minification (few very-long lines). Also **content/filename-based, not path-based** — same rationale as `looks_generated` — so a hand-written file under a directory named `lib/`/`vendor/` is still scanned.
- Both LLM stages share one usage dict so the **$2 spend cutoff** (`LLM_COST_CUTOFF_USD`) applies across the whole run. Past it, calls switch to the configured fallback provider — default **`none`**, which raises `LlmBudgetExhausted` so each stage records its remaining work as unverified (Ollama is optional, never assumed). With `regex_only` triage, the deep scan is effectively the only spender. Under parallel stages (below) the cutoff is also split into reserved per-stage shares.
- **Step banners name the tiers each stage actually holds** (`_tier_label`, `AgentTrace.set_label`): with `deep-scan-critical-only` on, step 7 prints `### Scanning CRITICAL files (deep scan)` and step 8 `### Scanning HIGH/MEDIUM/LOW files (triage)`. `scan_progress.PROGRESS_MARKERS` matches the `files (deep scan)` / `files (triage)` suffixes and the frontend anchors cards with `DEEP_SCAN_SECTION_RE`/`TRIAGE_SECTION_RE` (`lib/parseScanLog.ts`, `SectionCard.afterLabel` accepts a RegExp); both keep the old fixed `MEDIUM/LOW`/`CRITICAL/HIGH` strings for persisted logs.
- **Parallel stages** (`build_graph(parallel=True)`, limitation `parallel-scan-stages`, default on for API scans; CLI `--sequential`): after `derive_runtime_rules`, `fan_out` starts three stages that join at `group_triage_findings` — `flows` (`node_flows_branch`: discover -> verify -> Joern queries as **one** node, because LangGraph supersteps would make a chain wait for the slowest stage and the Joern session must not see concurrent queries), `scan_deep_files` and `scan_triage_files`. `usage` has a reducer (`_same_usage`) since every stage returns the same dict; interim Discovery reports merge tiers via `state["_partial_files"]`. Safety rails: `llm_client.reserve_stage_budgets` (deep 55%, flows 10%, triage/confirm 35% of the cutoff, mapped from LLM step names in `STEP_STAGES`; a stage may exceed its share only into unclaimed budget, and `finish_stage` releases its unused share), one process-wide `AdaptiveLimiter` (`LLM_MAX_CONCURRENCY`, default 8, halves on a throttle and regains a slot per 10 successes) around every provider call, throttle-specific jittered backoff that doesn't use up ordinary retries, a DB write lock in `scan_runner` (SQLite takes one writer), and a locked progress hook. Each stage runs under `state["_stage_log_context"]` (`scan_log.capture(scan_id, prefix="[[stage:<name>]] ")`, supplied by `agent_bridge`); `AgentTrace` banners are per thread, so sequential logs are unchanged. `scan_progress.ProgressTracker` ignores markers on tagged lines and counts each stage's `Stage finished: <name>` line instead (80% + weights), and `parseScanLog.ts` routes tagged lines to their stage's section while untagged/persisted logs parse positionally as before.
- **Joern (optional, `pipeline/joern_runner.py`)**: `node_build_joern_cpg` (after risk mapping) builds one CPG per dominant language. `node_discover_flows` merges `joern/flows.sc` taint paths (as `Flow`s with `taint_path`, `entry_tier="joern"`) with the tree-sitter call-graph flows before `verify_flow_slices`, and `node_joern_scan` (after triage) writes `joern/queries.sc` hits as `kind=joern` unverified findings and group-confirms them itself, since the triage group/confirm nodes skip under `llm_triage`. Joern flows also carry the CPG's control dependence (`Flow.guards`) and the `taint_spec.json` `sanitizers` the value passes through (`Flow.sanitizers`) into the verify prompt. These **annotate only, never drop a flow**; sanitized flows rank last. `flows.sc` runs sink kinds in `kind_order` (kept sorted by `call_graph._SINK_SEVERITY`, which a test enforces) and rewrites its output after each kind, so a timeout keeps the severe kinds (`complete: false`, read back via `run_script(allow_partial=True)`). `joern_runner` runs Joern with the CPG's temp dir as its cwd, because `importCpg` copies the graph into `./workspace/`; from the backend dir, those copies leaked into `backend/workspace/`. Without a Joern install every Joern node is a logged no-op and the report has no `joern` key. `tests/conftest.py` points `JOERN_HOME` at an empty dir so the offline suite never runs a local Joern; `pytest -m live tests/test_joern.py` runs the real one. See `backend/sast_engine/README.md` § Joern.
- **`node_corroborate_flows`** (`pipeline/reachability.py`) runs where the stages join, before `node_group_triage_findings` in both graph layouts. `node_discover_flows` indexes every Joern `flows.sc` path and every tree-sitter call-graph flow by sink (file, line) as `state["reachability_index"]`. It does this **before** the verify cap and before the deep-scanned-file drop, so it calls `discover_flows(cap=sys.maxsize)` and slices to the cap itself. The node attaches the best match (same file, ±2 lines, sink kind fitting the finding's CWE via `SINK_KIND_CWES`) to deep-scan, triage and Joern-query findings as `finding["reachability"]`, persisted as `Finding.reachability` (JSON) through `state["reachability_updates_writer"]` / `scan_runner._make_reachability_updates_writer`. The update is keyed like the verdict writer. Statuses: `path` (Joern taint path; raises a `true_positive` to `REACHABLE_CONFIDENCE_FLOOR` = 0.9), `sanitized_path` (Joern, through a sanitizer) and `entry_reachable` (call-graph method chain). The last two are attached only. **Evidence only adds: nothing is dropped or lowered for lacking a path.** Grouped confirmation lists the strongest-evidence members first (so they are the ones shown when the budget cannot show them all), puts each member's path in the prompt next to its excerpt and reapplies the floor per occurrence. Joern `kind=flow` findings get theirs in `flow_verify._findings_for_flow`. The report adds a `reachability` block when any evidence was attached. `group_unverified_findings` now stamps `file_path` from the file result onto regex and Joern-query findings, which never carried one. Before this, grouped confirmation sent an empty code excerpt and its verdict writer matched no rows (path `""`).
- **`node_generate_report`** produces TP/FP/**unverified** totals and OWASP-category counts (each category bucket has all three keys).

**The `unverified` verdict** is a third value alongside `true_positive`/`false_positive`, shared as `app.models.UNVERIFIED_VERDICT`. Nothing enforces it at the DB layer (`Finding.verdict` is a nullable `String(40)`, no enum), so the constraint lives in the code paths that branch on verdict — `llm_file_scan._VALID_VERDICTS`, `build_report_from_file_results`, `scan_runner._build_report_from_db_findings`, `scan_export._display_verdict` and the PDF pill colour, and the frontend's `verdictKind()`. Each of those had a two-way `if TP else FP` that would have silently mislabelled unverified findings as dismissed. Regex-only findings also deliberately **bypass `_should_publish_finding`**, whose whole purpose is suppressing LLM-invented findings on noisy rules — a regex hit is ground truth about what matched.

**The decision contract** (`app.models.VERDICTS` / `ISSUE_CLASSES` / `UNRESOLVED_REASONS`, mirrored in `llm_file_scan` because the engine cannot import `app`; `tests/test_verdict_contract.py` keeps the copies equal). Every finding has a `verdict`, an `issue_class` (`security` default; a rule opts into `quality`/`inactive` with its `issue_class` field, e.g. `serializable-missing-svuid`) and — when `verdict=unverified` — an `unresolved_reason` saying why nobody decided it (`not_reviewed_regex`/`_joern`/`_sca`, `llm_missing_verdict`, `llm_call_failed`, `llm_budget_exhausted`, `cap_reached`, `evidence_missing`). Every site that writes `unverified` sets the reason; `build_finding_row` stores `evidence_missing` (and warns) if one forgot. Old rows keep `NULL` in both columns and the API reports them as `null`, never a guess. `LlmBudgetExhausted` is now caught by name: a deep-scan chunk it hits gets the regex catalog run over just that line range (`_budget_fallback_findings`) and recorded `unverified`/`llm_budget_exhausted`, since a deep-scan file is not otherwise regex-scanned. The verdict updates writer writes only the keys an update carries (a group that could not be decided sends just `unresolved_reason`) and clears the reason once a verdict is decided. Review workflow is a separate state (`FindingReview`), never encoded in `verdict`.

**Occurrence identity and the version stamp.** `Finding.occurrence_id` is the sha256 of `project | file | rule | cwe | normalized sink expression | enclosing method signature | ordinal of the sink within that method` (`app/services/occurrence.py`) — **never the line**, so a blank line above leaves it unchanged while a changed sink expression or a different method changes it. The engine computes the file-dependent parts (`sast_engine/pipeline/occurrence.py`: tree-sitter enclosing method for Java/TypeScript/Python, ordinal = how many identical sink expressions precede it in the method, falling back to ordering for a paraphrased LLM sink) and stamps them in one place, `sast_scan_agent._findings_writer(state)`, which wraps `state["findings_writer"]` for every stage; `identity_quality` is `file_level` when no method resolved (YAML, XML, unparseable). It is a different thing from `feedback._fingerprint`, which hashes the *group* key and backs `FindingReview` — keep both. `group_findings_by_issue` also sets `member_occurrence_ids`. `Scan.metadata_json["versions"]` (`app/services/scan_versions.py`) records `engine_commit`, `rule_catalog_sha256`, `result_cache_version`, per-step `system_prompt_sha256` (from `llm_client.record_system_prompt`, filled in after the run) and the LLM provider/model; the mock engine records fixed `"mock"` values. Source files in this repo can be CRLF (`java.json`, `sca_scan.py`, `gates.py`, `test_findings_writer.py`): edit them byte-safely.

**Strict verdict parsing.** One pure parser, `llm_file_scan.parse_verdict(raw) -> (verdict | None, reason | None)`, is used by the deep scan and flow verify (`normalize_finding`), triage and group confirm. It accepts the exact enums (case-insensitive, `-`→`_`) and the aliases `tp`/`fp`/`true positive`/`false positive`/`confirmed`/`dismissed`; everything else — `"not sure"`, `"maybe"`, `"not a true positive"`, `42`, `["true_positive"]` — is `None` and the finding is written `unverified` with `llm_unrecognised_verdict` (nothing usable at all: `llm_missing_verdict`), the raw answer (≤200 chars) in `verdict_reason`, and `confidence=None` (`_normalize_confidence` no longer invents 0.7/0.5 for an unresolved verdict). There are no substring or negation heuristics and no default to `false_positive`; the old `_normalize_verdict`/`_strict_verdict`/`_NEGATION_RE` are gone (a test greps for them). A missing/unrecognised triage item is retried like a missing one, then recorded with its reason. Between duplicates of one issue `merge_dedupe` prefers true_positive > unverified > false_positive, and the noisy-SQL-concat publish check drops only a `false_positive` (an undecided answer is never dropped on a guess). `usage_summary` carries `unrecognised_verdicts`/`missing_verdicts` per step (`llm_client.record_verdict_event`). `RESULT_CACHE_VERSION` is `"2"`, so the first scan of each project after this change misses the cross-scan cache once.

**Accuracy corpus** (`backend/tests/accuracy_corpus/`, harness in `backend/accuracy/`, `pytest -m accuracy`, see its README). Small synthetic repos paired as positive/negative/uncertain cases, scanned with the **real graph** (`agent_bridge.run_real_scan` + the real `scan_runner` writers on a throwaway SQLite DB) against **recorded LLM responses** looked up by `result_cache_key` (provider + model + params + full prompt) in a file-backed `ReplayResultCache`, so a prompt/catalog change surfaces as "unrecorded LLM call" rather than a live call. Replay cannot reach the network: provider functions are stubbed to refuse, `AWS_*`/`OPENAI_*`/`ANTHROPIC_*` are removed from the environment for the run, and `agent_bridge._load_agent_module` is pinned for the run because it `importlib.reload`s `llm_client` on every call, which silently undoes any monkeypatch of it (and, unguarded, makes a "patched" run hit real Bedrock). `run_real_scan` takes two harness-only kwargs, `result_cache` and `state_overrides`. A case passes when its persisted findings are *exactly* its `expected` list; `xfail: EPIC-nn` marks a known gap (reported, and the run fails the day it passes). `ACCURACY_RECORD=scripted` rewrites recordings from each case's `scripted:` answers (no network); `=live` uses the real provider and spends money. Only `adjudicated` cases (a second reviewer agreed) are meant to gate releases.

**Verdict vs review state in the UI and exports.** `scan_export._display_verdict(value, unresolved_reason)` names each verdict as itself: `True Positive`, `False Positive`, `Unresolved (<reason>)`, anything else `Unknown (<raw>)` plus a logged warning — "Needs Review" is **not** a verdict label anywhere (it is a review *state*). Exports show the **scanner's** verdict (`llm_verdict`, which `feedback.apply_effective_verdicts` keeps when it overwrites `verdict` with the reviewer's) next to `review_state` (`feedback.review_state`: `pending` = no review or only "needs more info", `agreed`, `overridden`, `resolved` = resolution `resolved`/`risk_accepted`). The XLSX findings sheet has `Scanner Verdict`, `Review State`, `Issue Class`, `Unresolved Reason` and `Verdict (raw)` (find columns by header, not position); the PDF pill is the scanner's verdict with a `Scanner: … · Review: …` line, and the cover names the buckets Confirmed / Unresolved / False Positive (`verdict_bucket_totals`). Counting and grouping still use the *effective* verdict. Frontend: `lib/verdict.ts` `verdictKind` has a fourth kind `unknown` (null/unrecognised, never "dismissed"); `dastVerdictKind` maps it back to `dismissed` so DAST is unchanged.

**Decision history** (`finding_decisions`, model `FindingDecision`, `app/services/decisions.py`). `Finding.verdict` is the *current* value, updated in place; every verdict the scanner gave an occurrence is also an **append-only** row with the stage that decided it (`deep_scan`, `triage_regex`, `triage_llm`, `group_confirm`, `flow_verify`, `reachability_floor`, `joern_confirm`, `reconcile`, `sca_match`), `verdict`/`confidence`/`unresolved_reason`/`verdict_reason`, and `evidence_version` (the scan's `versions` block plus `result_cache_hit`). The latest row always equals `Finding.verdict`/`confidence` (a test checks the invariant). Rows are written by `_make_findings_writer` (initial insert), `_make_verdict_updates_writer` (every change of verdict *or confidence*; a no-op or a reason-only update writes nothing; the engine tags updates with `decision_stage`, the reconcile sweep passes `stage="reconcile"`) and `_make_reachability_updates_writer` (only when the floor raises confidence). They are written under the same `_DB_WRITE_LOCK`/transaction as the change, so a verdict can never move without its row. Nothing updates or deletes: the module exposes inserts only (a test holds it to that), the model raises `AppendOnlyError` on an ORM UPDATE/DELETE, and the only removal is the FK `ON DELETE CASCADE` when a scan's findings are bulk-deleted. The engine stamps `decision_stage` on each finding and `result_cache_hit` from `llm_client.last_call_was_cache_hit()` — a **thread-local** read in the same thread right after the call whose answer is parsed. `GET /scans/{id}/findings/{finding_id}/history` (`scans.view_own`, `authorize_scan`) merges this machine stream with the reviewer's `FindingReviewEvent`s in time order (read-side merge only: review state still lives on `FindingReview`); the scan's `usage_summary.decisions_by_stage` shows a stage that silently stopped writing. The findings panel shows it as a lazily loaded "Decision history" list.

**One count source.** `scan_export.count_findings(grouped)` is the only counting function (it replaced `count_groups_by_severity`): per verdict bucket (`true_positive`/`unverified`/`false_positive`) and severity, groups and occurrences; `totals`, `by_issue_class` (`unclassified` for legacy rows), `actionable`/`dismissed` (the shapes older clients read) and `by_owasp`. A group's bucket is its *effective* verdict via `_verdict_bucket` — the seam where mixed-verdict groups (EPIC-01) extend counting; a verdict outside the contract lands in an `unknown` bucket that still counts as actionable, never as dismissed. Group once per request (`group_findings_by_issue` mutates ORM instances) and pass the result around: `GET /scans/{id}/findings` (`tp_count`/`fp_count`/`unverified_count` are the bucket *occurrence* totals and `severity_group_counts` is the whole structure, both ignoring the verdict filter), the PDF cover/OWASP table, the Excel summary, `gates.build_gate_summary(project, findings, counts=)` and the findings panel's chips (`lib/findingCounts.ts` shows the server's numbers; there is no second implementation in the browser) all read it. `check_report_consistency(db, scan)` compares (1) the API counts with a recount of the API's own rows, (2) the Excel summary rows (`Groups — <bucket>`) with the rows of the findings sheet's `Counted As` column, and (3) the PDF cover note with the finding blocks (`FINDING n` headings, `Counted as:` in each block's verdict line) — an empty list means consistent; a real scan runs it at the end and logs contradictions as warnings without failing. `scan_runner._build_report_from_db_findings` (the engine report rolled up per *row*, persisted in `metadata`) is deliberately a different, occurrence-level tally. `pypdf` is a runtime dependency now (it reads the PDF back).

**Review-label import** (`scripts/accuracy/import_review_labels.py`, tooling outside the app). Joins the developer review workbook (R), the scanner Excel export (S) and optionally the scanner PDF (P) on `(file path, CWE, title)` — never on row number (the PDF holds four findings the workbooks do not, so its numbering shifts after #80). S is the hub; a join is `exact` (same CWE, same title, overlapping paths), `fuzzy` (truncated or near title — `needs_manual_review`, never auto-resolved) or `none` (one source only). Output is JSONL, one record per finding *per listed file* sharing a `group_ref`, with `scanner_verdict_R`/`scanner_verdict_S`/`scanner_label_P`/`dev_label_R` kept separate, `adjudication: dev_label_only` always, and no code or developer free text. The readers are header-driven (legacy and current Excel layouts), R's columns are configurable (`--review-columns`). The real R/S/P files are supplied by the project owner and never committed; `backend/tests/test_import_review_labels.py` uses a synthetic triplet.

**Rescan decision diff** (`app/services/decision_diff.py`). `GET /scans/{id}/decision-diff?base=<scan_id>[&include_unchanged=true]` (and `.xlsx`, `reports.export`) compares two SAST scans of one project **joined only on `occurrence_id`**: per occurrence `added`/`removed`/`verdict_changed`/`issue_class_changed`/`unchanged` (unchanged omitted by default), old and new verdict/class/reason/confidence, the *new* decision's stage and reasoning, and both scans' `evidence_version` (so you can tell whether the scanner itself changed). It reads the scanner's own `Finding.verdict` (not the reviewer overlay) plus each finding's latest `FindingDecision`. The summary lists transitions with `true_positive → false_positive` and `true_positive → removed` first — a scanner change is judged by those, not by how many rows it removed. Several rows sharing one id collapse to the strongest (true_positive > unverified > false_positive); `file_level` identities join but are flagged. Both scan ids go through `authorize_scan` (an out-of-scope base is a 404); a base in another project, a non-SAST scan, or a scan whose findings have no occurrence ids is a 422 with the reason; a different commit is allowed and flagged `commit_differs`. `diff()` is pure over plain records, so the release gate reuses it. The scan header has a "Compare with…" panel (`ScanDecisionDiffPanel`).

**Accuracy release gate** (`python scripts/accuracy/gate.py --baseline backend/tests/accuracy_corpus/accuracy_baseline.json`, library in `backend/accuracy/gate.py`). A thin orchestrator over `accuracy.runner` (scan each case, with `check_consistency=True`), `scan_export.check_report_consistency` and `decision_diff.diff`; replay only, never a live call. Five gates: (1) a `positive` case's expected true positive is missing or no longer one; (2) a `negative` is not a false positive, misses its `reason_tag`, or vanished (unless `allow_absent`); (3) an `uncertain` case resolved instead of staying `unverified` with the expected reason; (4) a report contradiction in any corpus scan; (5) against the committed baseline an occurrence went true_positive → false_positive/absent — **even for an `xfail` case**. Gates 1-3 count only `adjudicated` (second reviewer agreed), non-`xfail` cases; `dev_label_only` cases are listed under "Not gated"; gates 4 and 5 are about defects, not labels, so they cover every case. Occurrence ids are reproducible because `run_case` derives the project/scan ids from the case id. `--update-baseline` rewrites the baseline and refuses while gate 1 or 5 fails. Output: `accuracy_gate.md` (gate by gate, then cases) and `accuracy_gate.json`. `.github/workflows/accuracy-gate.yml` runs it on changes under `backend/sast_engine/**` and `scan_export.py` (the repo's first workflow; not yet run on GitHub). Stories in EPIC-01..03 that change a rule, prompt or filter list "gate green" in their Definition of Done (`spec/dev-stories/sast-accuracy/README.md`).

Naming note: the graph nodes, the `llm_step`/usage `step` keys, and the `### ` log banners were renamed from `scan_critical_files`/`scan_low_files` when MEDIUM moved tiers. `scan_progress.PROGRESS_MARKERS`, `frontend/lib/formatUsage.ts`, and `frontend/lib/parseScanLog.ts` all deliberately keep the **old** strings alongside the new ones so already-persisted scans still render.

### Ripgrep prefilter and LLM providers

The agentic hunt (`pipeline/hunt/`, node `hunt_security`, learned rules) was removed: it spent budget without adding findings. Old scans can still hold `kind=hunt` rows, which `scan_runner.reconcile_unverified_findings` skips because their `unverified` is an evidence cap. The frontend keeps the hunt's log and usage-step strings so those scans still render. Ripgrep stays, for the triage catalog prefilter only (`pipeline/rg_prefilter.py` → `pipeline/rg_runner.py`, limitation `ripgrep-catalog-prefilter`). It ships via the pinned `ripgrep` wheel in `requirements.txt` (`RG_PATH` overrides) and runs under a `ulimit -v` shell wrapper (Linux-enforced). `config/`/`configuration/` directories are walked (only their data files are excluded, `llm_file_scan.config_dir_file_is_scannable`) — they used to be pruned, hiding `com/<pkg>/config/*.java` from every tier.

SAST LLM providers are `bedrock`, `openai_compat` (any OpenAI-compatible `/chat/completions`; per-project `llm_base_url` + write-only `llm_api_key`, exposed only as `llm_api_key_set`, never snapshotted onto `Scan`) and optional `ollama`; an unknown provider raises instead of silently using Bedrock. There is no per-project data policy: any configured provider may receive repository code. Provider constants: `app/services/llm_policy.py` (mirrored in `llm_client.py`, which the app can't import); `agent_bridge.llm_usage_options` builds the per-scan `init_usage` options for both the scan and the reconcile sweep.

### LLM token efficiency

Every array-returning LLM stage (deep scan, flow verify, triage, group confirm, rule derivation) uses `json_mode=True` with an **object envelope** (`{"findings": [...]}`, `{"decisions": [...]}`, `{"rules": [...]}`) — Bedrock JSON mode prefills `{`, so a bare-array schema forced salvage parsing and full-prompt retries. `llm_client.parse_llm_json_array` unwraps the envelope, and treats a well-formed empty one as a clean answer, never a parse error. Bare arrays still parse (Ollama, older fixtures).

- **Stable, cacheable system prompts.** The output schema lives in the system prompt (`llm_file_scan.build_system_prompt`, `flow_verify.build_flow_system_prompt`), and the catalog is rendered one line per rule (`render_catalog`, no per-rule OWASP — `normalize_finding(rule_owasp=...)` fills it locally). User prompts carry only per-chunk content. `llm_client.should_cache_system_prompt` attaches a Bedrock `cache_control` checkpoint once the system prompt clears the model minimum (4096 tokens for Haiku/Opus, 1024 otherwise; `BEDROCK_PROMPT_CACHE=0` disables) — in practice the Java deep-scan prompt. `input_tokens` stays the *logical* prompt size; `cache_read_input_tokens`/`cache_write_input_tokens` only discount `cost_usd` (0.1×/1.25×). The first call per (model, system prompt) runs alone under a warm-up gate (`_warm_gate_for`, re-armed after `PROMPT_CACHE_WARM_TTL_SECONDS`=240) and the rest fan out once it has returned — Bedrock only reads an entry after the writing call completes, so without the gate parallel workers each paid the 1.25× write (a 9-file scan saw 3 writes and 1 read, ~break-even). A failed leader leaves the gate cold so the next waiter takes over.
- **Less repeated input.** Multi-chunk files get a per-chunk skeleton (`skeleton_for_chunk`: entries inside the chunk dropped, `SKELETON_CHUNK_MAX_CHARS` cap, taint lines first), and a leading license header is collapsed to one marker line with true line numbers kept (`leading_license_header_span`). The deep-scan `snippet` field is now just the flagged line — it is still needed by `reanchor_line` and suppression, so don't remove it.
- **Slim deep-scan output.** Output tokens cost 5× input and the cached system prompt reads at 0.1×, so the response schema (`llm_file_scan._RESPONSE_SCHEMA`) is the bigger lever than the prompt text. A finding citing a catalog `rule_id` may omit `title`/`cwe`/`owasp_category` (`normalize_finding(rule_meta=catalog_rule_index(catalog))` fills them — the filled CWE is what keeps it past `suppress_no_cwe`), and a `false_positive` omits `source`/`sink`/`data_flow`/`ai_fix`. `llm-extra` findings still carry their own title and CWE. `verdict` is emitted before all of these, so dropping them doesn't remove reasoning that fed the verdict.
- **Triage is decision-only.** `triage_regex_hits` dedupes hits on (rule, line), gives them ids `c1..cn`, merges overlapping ±10-line windows (`merged_context_windows`), and lists each rule's description once. The model returns `{id, verdict, confidence, verdict_reason, severity?, ai_fix?}`, and everything else is filled from the rule. **Every candidate gets an outcome**: missing ids get one follow-up call with only their excerpts, and anything still undecided (or with an unrecognised verdict — `parse_verdict`) is written as `unverified`, never dropped or defaulted to `false_positive`. Older `rule_id`+`line` items are still matched (`resolve_triage_decisions`).
- **One flow verification per sink.** `call_graph.collapse_flows_by_sink` keeps the best-ranked flow per (sink file, line, kind), for Joern flows (in `flows_from_joern`, before the cap) and call-graph flows. The other entry points are listed on it as `Flow.other_sources` and named in the verify prompt (`flow_verify.build_other_sources_note`). Several endpoints reaching one DAO call used to cost one call each and produce the same finding 3–4 times. The reachability index is built from the uncollapsed lists.
- **Small deep-scan files share a call when their prompt isn't cached.** `scan_deep_files` packs files under `BATCH_FILE_MAX_CHARS` (6,000, single chunk) into batches (`plan_deep_scan_batches`: ≤ `BATCH_CHAR_BUDGET` 16,000 chars, ≤ `BATCH_MAX_FILES` 8, one language each), but only when `system_prompt_is_cached` is false. That covers a non-Bedrock provider or a prompt under the model's cache minimum (Haiku's 4,096 tokens; in practice the TypeScript/HTML/XML/YAML prompts, while Java's clears it). `scan_file_batch` asks for a `"file"` field per finding and routes by exact path, unique suffix or unique basename. Unroutable findings are counted in `chunk_errors`, never misfiled. A failed or unparseable batch falls back to one `scan_file` per file. `state["deep_scan_batch_small_files"]` / CLI `--no-batch-small-files` turns it off. On an Angular + Spring repo this cut deep-scan calls from 104 to 46 and billed deep-scan input by about half.
- **Flow verification batches shared hops.** Flows that share a hop method are verified together (`group_flows_by_shared_hops`, `FLOWS_PER_CALL`=3, `FLOW_GROUP_CHAR_BUDGET`): each distinct hop is printed once as `[H<n>]` and findings are routed by `flow_id` (`assign_items_to_flows`). A slice over `FLOW_SLICE_CHAR_BUDGET` condenses *intermediate* hops to the signature plus windows around the call line and Joern path lines; entry and sink hops always stay whole. An unparseable response counts in `flows_failed`, not `flows_verified`.
- **Cross-scan result cache.** `llm_client.call_llm` consults `usage[RESULT_CACHE_USAGE_KEY]` (a `get`/`put` object riding on the shared usage dict), keyed by `result_cache_key` = sha256 of `RESULT_CACHE_VERSION` + provider/model/params + full system + user prompt. Only JSON-mode responses that are complete (`is_complete_json_response`: no `max_tokens` stop, parses without salvage) are stored. `agent_bridge.run_real_scan` attaches `app/services/llm_result_cache.DbLlmResultCache(project.id)` (table `llm_result_cache`, deleted with the project) unless the scan's `metadata.bypass_llm_cache` is true. Hits make no call and add no tokens; they're reported as `result_cache_hits`/`result_cache_saved_tokens` in `usage_summary` (and per step). **Bump `RESULT_CACHE_VERSION` whenever response handling changes but prompt bytes don't.** Rule derivation is cached too, which is what keeps the deep-scan system prompt (which embeds derived rules) byte-identical on reruns. That only works if the derive response is *complete*: a truncated answer is never stored, and the old ask of up to 50 rules against a 4096-token ceiling was cut off after ~24 on every scan. `llm_derive_rules` now asks for at most `PASS_B_MAX_RULES_PER_CALL`(=30) and sizes `max_tokens` to the ask (~220 tokens/rule + headroom, capped at 8192) — so `max_derived_regex_rules` > 30 no longer raises the Pass B ask, only Pass A's share. The CLI has no cache.

### Per-occurrence decisions (EPIC-01)

A decision is made for one concrete occurrence *before* findings are grouped, and nothing downstream may copy one occurrence's verdict to another that differs. The pieces, in the order a finding meets them:

- **Occurrence facts** (`pipeline/occurrence_facts.py`, Java + TypeScript, tree-sitter, pure: source text in, facts out). `facts_for(path, text, line, match_span, sink_hint=)` returns the enclosing method (owner, name, parameter types, arity, line span), `is_declaration`, `is_stub`, the `call` at the anchor (the outermost invocation starting on that line, narrowed by the regex match's columns or the LLM's `sink`: callee, receiver text, receiver FQN or declared simple type, arity, start position, source text), one `args` entry per argument (`kind` ∈ string_literal/constant/numeric/boolean/enum/string_var/call_result/throwable/object/unknown, plus a `via` receiver type for call-result arguments), `in_comment`, and the enclosing `statement`. Numeric/constant kinds describe the value *actually used* (`Long n = parse(s); sql + s` is `string_var`); `BigDecimal` is `numeric` only from `new BigDecimal(..)`/`valueOf`/`getBigDecimal`. It returns `None` — and every consumer then behaves exactly as before facts existed — without tree-sitter, for an unsupported language, or when the anchor sits in a region tree-sitter had to repair. Parses are cached (bounded LRU, one per file text). Regex hits now carry `col_start`/`col_end` for this. `finding_facts.prepare_findings` is the one entry point the stages call (deep scan, batch, regex triage, flow verify) before dedupe: it attaches facts, runs the validators, and marks findings `_prepared` so a retry never repeats it. Facts persist as `Finding.facts` (JSON, ≤ 2 KB).
- **Validators** (`pipeline/validators/`, scan limitation `occurrence-validators`, default on; `state["occurrence_validators"]`, CLI `--no-occurrence-validators`). Registered by rule id/prefix/CWE; each answers `negative_proof` / `positive_fact` / `evidence_gap` / `no_opinion`. **Precedence is fixed:** negative proof → `false_positive` with the proof as the reason and a `reason_tag` (a regex hit with a proof is still written as a row); positive fact against a model `false_positive` → `unverified`/`conflict`; evidence gap → `unverified`/`evidence_missing`; negative > positive > gap. Outcomes are kept in `facts["validators"]` so group confirmation re-applies the table to the model's later verdict (`reapply_precedence`). Shipped: `stub_method` (`stub_no_sink`) and `declaration_not_call` (`match_is_declaration`) for `runtime-sink-*` rules. A validator must never return a negative proof from a rule name, path, logger spelling or severity (see `validators/base.py`).
- **Publish filters** (`llm_file_scan.publish_decision` → `PUBLISH`/`DROP`/`DEMOTE`; `should_publish_finding` is its bool wrapper). A finding on a logger call is dropped only when its CWE is one a log call cannot be (`LOG_LINE_IMPOSSIBLE_CWES`: 89/79/78/22/611/918/502/90), and "is a logger call" comes from the resolved receiver type (any slf4j/log4j/jul/commons-logging/jboss logger under any variable name, `console`, `NGXLogger`); `_LOGGING_CALL_RE` is only the fallback for findings without facts. Secrets and forged log content (CWE-532/117/312/…) are published. A noisy SQL-concatenation true positive is published as a true positive only if its **own statement** builds the query or its named `source` is really in the enclosing method (or on the flow path); otherwise it is `DEMOTE`d to `unverified`/`evidence_missing`. Confidence never substitutes (`UNEVIDENCED_CONFIDENCE_FLOOR` is gone). Drops and demotions are counted in `usage_summary.publish_filter`.
- **De-duplication** (`merge_dedupe`): two findings merge only if they are about the same call node (equal `facts.call` start); without facts the old line window applies. Between a confirmation and a dismissal of one node a validator proof wins, then more evidence (source/sink/data_flow + sink on the anchored call), and on equal evidence the result is `unverified`/`conflict` with both reasons — the more alarming verdict is no longer taken by default. Each merge leaves a `dedupe` decision row.
- **Semantic group keys.** `group_key_for_finding` and `scan_export._finding_group_key` both end with `semantic_signature(facts)` (callee owner + name + arity | receiver type | argument kinds; declarations by method name, arity and stub-vs-implementation). The two signature functions are mirrored (`occurrence_facts.py` / `app/services/occurrence.py`) and `tests/test_group_key_parity.py` keeps them and the two key functions equal. Members without facts group only with each other.
- **Per-member grouped confirmation** (`confirm_finding_group`/`_batch`). A prompt carries a numbered excerpt per member (`m1..mN`, windows of one file merged, resolved facts and validator facts alongside) up to `GROUP_CONFIRM_MEMBER_CHAR_BUDGET`, ordered by (reachability strength, path, line) so prompts are deterministic; groups are ordered by size then key. The model answers one decision per member id. A group whose members share a signature *and* a normalized excerpt takes one decision for all (`uniform`). Members left out of the response, and members the budget could not show, get **one** follow-up call; what is still undecided is `unverified` — `llm_missing_verdict` if it was shown, `not_in_sample` if it never fit, `llm_budget_exhausted`/`llm_call_failed` on provider failure. **No member inherits a sibling's verdict.** Each member records `review_coverage` ({reviewed, total}) and "Reviewed k of N occurrences". `llm_triage` mode follows the same rule for repeated matches beyond `TRIAGE_GROUP_WINDOWS`. The reconcile sweep rebuilds finding dicts *with* `facts` so it groups as the scan did.
- **Explanation check** (`pipeline/explanation_check.py`; same toggle). Five checks — sink not in the anchored call, source not in the method/flow path, a TP whose reason says "safe" (or an FP whose reason asserts exploitation; negated phrases ignored), a suggested fix the code already contains, an unproven "no callers" claim (the call graph counts as incomplete until SAST-02-070) — run on deep-scan, flow-verify and group-confirm results. A contradiction earns **one** retry (same prompt + a `Deterministic facts:` block) if `stage_has_budget`; a consistent retry replaces the answer, otherwise the finding is `unverified`/`explanation_contradiction`. **It is never turned into a false positive.** Sources are matched on their callee name so `TextMessage.getText()` matches `message.getText()`.
- **Mixed constructs.** `annotate_construct_mix` (run inside `group_findings_by_issue`) puts `construct_key` and `construct_mix` ({tp, fp, unresolved} in *members*, across all rows of the construct) on every grouped row; the API, the Excel "Construct Mix" / "Reviewed / Total" columns, the PDF verdict strip and the UI chip all read them, and `check_report_consistency` compares them. A first review of a row whose construct is mixed is refused with 409 unless it names `member_ids` or `apply_to: "all"`.
- **Bookkeeping.** `usage_summary` gains `validators`, `publish_filter` (+ `publish_filter_drops`), `dedupe_conflicts`, `explanation_contradictions`, `group_confirm_coverage` and `facts_coverage` (counters via `llm_client.bump_counter`; dotted keys nest) and per-step `members_reviewed/total/not_in_sample`. Steps between the model's answer and the stored verdict (validator, dedupe, publish_filter, explanation_retry) ride on `finding["decisions"]` and become `finding_decisions` rows with `actor` and `detail`. `RESULT_CACHE_VERSION` is `"4"`.

#### SQL semantics (EPIC-02)

A CWE-89 finding means external text can change the *executed SQL grammar*; the `sql_binding` validator decides that from structure, not from text near a line. All of it is deterministic (no LLM) and rides the validator hook above.

- **`pipeline/sql_semantics.py`** (pure: source in, facts out; reuses `occurrence_facts`' parse cache and argument kinds and `call_graph`'s type table, no resolver of its own). `statements_in_method` returns one `StatementFact` per JDBC statement allocation (`prepareStatement`/`prepareCall`/`createStatement`, or a `JdbcTemplate` call with `bound_by_args`): its query node, its `setXxx` binds (index, value kind) and its executions, each tagged with the branch (if/else arm, switch group, loop) it sits in. Comments are never part of an expression. A `PreparedStatement` executed with its own SQL string is `api_misuse`. `classify_query` folds the query (`+`, `StringBuilder`/`+=` appends incl. loops, `String.format`/`MessageFormat`/`String.join`, single-assignment locals, `static final` constants, other classes' constants the repo resolves) into `fixed` / `fixed_placeholders` / `dynamic_value` / `dynamic_identifier` / `unknown(resolver)`; placeholder lists (`?,` loops, `nCopies`, `repeat`) are fixed grammar. `judge_statement` is the one judgement the validator and the summaries share.
- **`sql_binding`** (`validators/sql_binding.py`; rules `java-sql-string-concat`, `java-jdbc-prepare-concat`, `java-jdbc-statement-exec-variable`, `runtime-sink-sql-*`, and any CWE-89 finding). Negative proofs: `sql_fixed_template_bound` (fixed text, every placeholder bound on every path; a finding on a setter gets it too), `sql_numeric_only` (only numbers concatenated: `issue_class=quality`, a hygiene issue), `sql_api_misuse_constant` (`quality`), `sql_callee_no_sql`. Positive facts: `sql_dynamic_text`, `sql_api_misuse_dynamic`, `sql_second_order` (a `ResultSet` text column reused as SQL text: `origin=persisted`). Anything unresolved is a *named* evidence gap, never a guess. The prompt gains one sentence: a `PreparedStatement` setter value is data, not SQL text. Proof text is capped at 200 chars, so put the load-bearing words first.
- **Method summaries** (`SqlSummaries`, per scan, demand-driven, memoised): does a method execute SQL (`none`/`fixed_bound`/`dynamic(parameter positions)`/`unknown(reason)`), what SQL it returns (`fixed`/`placeholder_list`/`dynamic`) or appends to a builder it is handed. Calls resolve by receiver and signature through `call_graph.resolve_targets` (a facade = the union of its implementations; same-arity overloads stay apart); flow-discovery edges are unchanged. Depth is bounded (6) and so is summarising time; a pure recursion cycle is `unknown/cycle`. Counters: `usage_summary.sql_summaries`. The Java call graph is built for the validators even when `inter-file-call-graph` is off (no ranking, no flows); the scan's `ValidatorContext` (repo root, graph, summaries) rides on `usage["_validator_ctx"]`.
- **Wrapper rules by method identity** (`derive_rules.wrappers_from_graph`): a `runtime-sink-sql/jpa/jdbc_template` rule is derived only when the wrapper's summary shows a *parameter* reaching SQL text. Fixed-bound, zero-argument, getter and stub wrappers derive none. The id is `runtime-sink-<kind>-<name>-<8 hex of owner+signature>`, byte-stable across runs; the rule carries `wrapper_owner`/`wrapper_signature`/`wrapper_arity`/`tainted_params` (`RegexRule.wrapper`, copied onto hits). `wrapper_call_identity` then dismisses a call that resolves to another owner or arity (`wrapper_identity_mismatch`) or passes only constants at the tainted parameters (`wrapper_arg_constant`). Changing the derived ids changes the deep-scan system prompt once (expect one cache-missing scan per project).
- **Entry points and inactive code** (`pipeline/entry_points.py` + `call_graph.reachability_status`): descriptors (`web.xml`, `ejb-jar.xml`, `webservices.xml`, `sun-jaxws.xml`, `faces-config.xml`, Spring XML beans), `@Remote`/`@Local` interfaces, JMS `onMessage` and `Class.forName`/`getMethod` strings are entry points, each with its source. `unreferenced` is claimed **only for a private method** with no call (resolved or unresolved, by name and arity), method reference, reflection name or other mention, and full parse coverage; then unsafe SQL in it stays a true positive with `issue_class=inactive`. Narrower than the spec on purpose: a public method nobody in the repo calls may be called from a JSP, EL, a framework config or another module.


### Rule catalog and vulnerability surfaces

`backend/sast_engine/rules/` holds the regex catalog split per language (`java.json`, `xml.json`, `typescript.json`, `python.json`, `web.json`, `common.json`); `regex_scan.load_rules` accepts a directory or a single file and raises on duplicate ids. This replaced the old single `regex_rules.json`.

- `rules/surfaces.json` maps detected stack signals to named vulnerability surfaces and the rules covering them — the `Tech Stack Detected -> Known Vulnerability Surface -> Targeted Regex` reasoning from the legacy audit docs in `backend/sast_engine/regex_data/`, made reproducible for any repo. **Surfaces narrate and prioritize the prompt catalog; they never gate a rule**, so a mistyped surface can't reduce coverage. The "REST exception and CORS exposure" surface triggers on JAX-RS *and* Spring Boot/Framework/Security, but until `spring-exception-message-in-response-body` and `csrf-disabled` were added to its `rules` list, the only rule it actually listed for exception-in-response exposure (`jaxrs-exception-in-response-entity`) was JAX-RS-framework-scoped and could never fire for a Spring app — a surface entry referencing a rule doesn't make that rule match anything outside its own `frameworks` filter. `csrf-disabled`'s pattern originally only matched a `.csrf(...disable` idiom appearing on a **single physical line** — `regex_scan.py` only scans a rule in multiline mode when its pattern literally contains `[\s\S]`/`[\S\s]`, and this one didn't, so Spring Security 6's lambda DSL (`.csrf(csrf -> csrf.disable())`) silently missed whenever a formatter wrapped it across lines, which is common. The pattern now includes a bounded `[\s\S]{0,200}?` between `.csrf(` and `disable` specifically to opt into multiline scanning. `spring-exception-message-in-response-body` had the same class of gap: it matched `ex.getMessage()` passed inline or DTO-wrapped into `.body()/.ok()`, but not the more common idiom of assigning the message to a local variable first — a second alternative branch (also multiline-bounded) now catches that. A dedicated `java-log-injection-unsanitized-input` rule (wired into the "Logging and error disclosure" surface, `when: {}`) was added since no existing rule covered unsanitized exception/request data reaching a logger call — `java-sensitive-data-in-logs` only matches sensitive *keywords*, and `logger-exception-tostring` is an unrelated info-disclosure rule. Checking `csrf-disabled` against the actual target-repo source afterward showed the real code used `.csrf(AbstractHttpConfigurer::disable)` on a single line — which the *original* pattern already matched — so the multiline gap, while real and worth fixing defensively (a formatter commonly wraps the lambda-DSL form across lines), was not the actual cause of that specific miss; the multiline fix stands as a real robustness improvement, just not the explanation for that one report.
- Rules take three independent, empty-means-universal filters: `languages`, `frameworks` (must match a `stack_signatures.py` label exactly), and `requires_dependency` (name + optional `version_lt`/`version_lte`). The last one matches against `dependency_summary.declared_dependencies` — *every* declared dependency, not just signature-matched frameworks, since the libraries that matter here (commons-collections, jsch, castor) aren't frameworks. **Unknown/unparseable versions fail open.**
- A rule's `group_by_rule` field (default `false`) controls how its unverified regex findings collapse in the report/export and during grouped LLM confirmation. Findings normally group on `(rule_id, matched_text)` — deliberately, so a real hardcoded credential and a test placeholder that trip the same rule stay separate rows (`app.services.scan_export._finding_group_key`, `llm_file_scan.group_key_for_finding`). A rule whose matched text is *expected* to differ every occurrence while still describing one issue sets `group_by_rule: true` to collapse by `rule_id` alone instead: `serializable-missing-svuid` (class name baked into `class Foo implements Serializable`), `logger-exception-tostring` (the exception variable name baked into `logger.error(..., ex.toString())`), and `java-path-file-constructor` (the path variable name baked into `new File(userPath)`/`Paths.get(configuredDir)`). `java-sensitive-data-in-logs` deliberately does **not** opt in despite similarly-varying matched text — which sensitive keyword matched (password vs ssn vs token vs ...) is security-relevant, not cosmetic, so collapsing it would hide that distinction. The flag is set once on `RegexRule`, denormalized onto the finding dict at hit-time (`llm_file_scan.findings_from_hits`) and onto the `Finding.group_by_rule` DB column at write time (`scan_runner._make_findings_writer`) — so nothing downstream ever needs the rule catalog to decide how to group. Prefer a zero-width lookahead over a consuming quantifier for "doesn't appear nearby" patterns (see `rules/README.md`) — a consuming match drags variable trailing content into `matched_text`, which defeats grouping on its own even for otherwise-identical hits; `group_by_rule` is the right fix instead when the captured span is short (a variable/keyword token) rather than a runaway trailing match.

Every new rule ships `examples` (`{match, no_match}`), which `tests/test_rule_catalog.py` runs through the real scan path; `scan_comments` opts a rule out of comment masking (multiline hits are masked too now), and multiline rules report every match up to 25 per file. See `backend/sast_engine/rules/README.md` for the field reference and `backend/sast_engine/README.md` for the pipeline breakdown.

`backend/app/services/agent_bridge.py` bridges `scan_runner.py` into this agent: it dynamically `importlib`-loads `sast_scan_agent.py` from `settings.sast_framework_path` (default in-repo `backend/sast_engine`) rather than importing it as a package, specifically so the mock-engine test suite never needs `boto3`/`langgraph` installed. Real engine deps (`boto3`, `langgraph`, `tree-sitter*`, `semgrep`, ...) are only needed when actually exercising this path.

**Note:** the root `README.md`'s "Dual finding sources" / "graph SAST v3" / OWASP+NVD reference-scan description and `.env.example`'s `RUN_REFERENCE_SCAN`/`RUN_SEMGREP`/`RUN_REGEX_SCAN` commentary describe an even older, since-removed architecture (AST/semgrep-based detection, removed in "Remove AST-based vulnerability detection" and "Simplify SAST to a discovery agent") that predates the current LLM-based findings scan — trust `backend/sast_engine/README.md`, `agent_bridge.py`, and `sast_scan_agent.py`'s own docstring over those when they conflict.

### Per-project scan limitations

`backend/app/defaults/scan_limitations.py` defines a fixed catalog of togglable checks (engine caps, analysis checks, security patterns). `Project.limitations_config` (JSON column) stores which are enabled; `GET /scan-limitations` lists the catalog and `PATCH /projects/{id}/limitations` updates a project's config. Surfaced in the frontend at `/projects/[id]/settings` (`ScanLimitationsPanel.tsx`, which renders whatever the catalog returns generically — no ids hardcoded there). Entry ids are referenced by `tests/test_scan_limitations.py`, so renaming one means updating that test too.

Most catalog entries are **display-only** — they document an existing hard-coded engine behavior (the $2 Bedrock cutoff, the 100-file deep-scan cap, ...) but nothing reads `limitations_config` back to actually change that behavior. The exceptions, and the pattern to follow for any future real toggle: `agent_bridge.run_real_scan` reads `project.limitations_config.get(<id>, <enabled_by_default>)` and threads the result into `initial_state`, which the relevant node/pipeline function reads via `state.get(<key>, <default>)`.

- **`cwe-less-findings-suppressed`** (default **on**) → `state["suppress_no_cwe_findings"]` → `llm_file_scan.should_publish_finding(suppress_no_cwe=...)`: drops a deep-scan (`kind=llm`) finding outright when the LLM returned no CWE mapping — too generic to act on. Regex-tier findings are unaffected (every catalog rule always carries a CWE).
- **`https-enforced-suppress-http`** (default **off**, per-project opt-in) → `state["suppress_http_findings"]` → `should_publish_finding(suppress_http_findings=...)`: drops deep-scan findings describing cleartext HTTP transmission / missing HTTPS enforcement (`llm_file_scan._HTTP_FINDING_CWES` = CWE-319/311/523/757, or a title/`verdict_reason` matching `_HTTP_FINDING_RE`). Necessarily heuristic — there is no regex rule for this (the catalog has none), and the scan has no way to independently verify a project's HTTPS posture (load balancer, reverse proxy, and platform TLS termination are all invisible to it), which is why this defaults off and is opt-in per project rather than auto-detected.
- **`low-confidence-fp-suppressed`** (default **on**) → `state["suppress_low_confidence_false_positives"]` → `should_publish_finding(suppress_low_confidence_false_positives=...)`: drops a deep-scan finding the model itself marked `false_positive` with `confidence <= llm_file_scan.FALSE_POSITIVE_SUPPRESS_CONFIDENCE_CEILING` (0.2; confidence is documented in the LLM prompt as "how sure you are this is exploitable", so low confidence on a `false_positive` verdict means a confident dismissal). Unlike the noisy-SQL evidence rule (below — confidence no longer publishes anything there), this is a general net over every rule and only ever drops `false_positive` findings — export-time these were relabeled "Needs Review" (`scan_export._display_verdict`) regardless of how confidently the model had already dismissed them, which is exactly the noise this removes.

The three checks above live in `should_publish_finding`/`finalize_findings`/`scan_file`/`scan_deep_files`, threaded down from `node_scan_deep_files` — CLI-only via `--allow-no-cwe-findings` / `--suppress-http-findings` / `--suppress-low-confidence-false-positives` when not going through `agent_bridge`.

- **`test-files-skipped`** (default **on**, display-only) documents `llm_file_scan.is_test_path`; **`parallel-scan-stages`** (default **on**) is a real toggle read by `agent_bridge` (see Parallel stages above).
- **`vendored-minified-files-skipped`** (default **on**, display-only like `generated-code-skip` — unconditional engine behavior, no per-project toggle) documents `llm_file_scan.looks_vendored_or_minified` (see above).

### Scan lifecycle

`scan_runner.execute_scan` drives a scan through `queued -> running -> success/failed`, run inline for the mock engine (deterministic, synchronous, test-friendly) or on a daemon thread for the real engine (`start_scan_background`). It:

1. Snapshots the project's LLM provider/model onto the `Scan` row at start (`Scan.llm_provider`/`llm_model` etc.) so history doesn't drift if the project's settings change later.
2. Checks out the workspace via `git_workspace.ensure_workspace` (real engine only — the mock engine never touches git).
3. Calls `engine_adapter.run_scan`, capturing engine `print()` output via `scan_log.capture`/`scan_log.register_line_hook`, which also drives `Scan.progress` by matching lines against `scan_progress.PROGRESS_MARKERS`.
4. Persists the engine's `discovery`/`report`/`usage_summary` output onto `Scan.metadata_json`; `Finding` rows are written incrementally during the LLM scan stages rather than in one batch at the end (so results — via `GET /scans/{id}/findings` — can appear mid-scan).

`GET /scans/{id}/logs?after=<seq>` exposes this same log tail incrementally to the frontend's "Engine log" panel (`ScanAgentLog.tsx` / `parseScanLog.ts`). The frontend splits results across two panels — `ScanDiscoveryPanel.tsx` (tech stack/risk mapping) and `ScanFindingsPanel.tsx` (severity/verdict-filterable findings) — and `GET /scans/{id}/export.pdf` / `export.xlsx` (`scan_export.py`, proxied via `frontend/app/api/scans/[id]/export/[format]/route.ts`) export the findings report.

**Finding grouping.** `GET /scans/{id}/findings` and both exports don't return raw rows — `scan_export.group_findings_by_issue` collapses them first, keyed by `(verdict, "rule", rule_id, normalized matched text, semantic signature)` in `_finding_group_key` (the signature is explained under **Per-occurrence decisions**; rows without facts all carry `unresolved`, so old scans group as they always did). The matched text (`Finding.matched_text`, the literal regex match, not the multi-line `snippet` context window) is what keeps genuinely different code separate while collapsing one construct repeated across hundreds of files into a single row listing every location in `affected_files`. This matters far more since the regex-only triage tier: there is no LLM filtering the volume any more, so grouping is the only thing keeping the list readable. Note that the representative-picking logic **mutates the ORM instance** (`representative.affected_files = paths`, `occurrence_count`) — safe only because nothing flushes or commits afterwards. Headline counts everywhere (PDF strip, Excel summary, OWASP table, `severity_group_counts` on the findings response, the panel chips) come from `scan_export.count_groups_by_severity`: actionable (true positive + unverified) **groups** with their occurrences per severity, dismissed groups shown separately. There is no pagination or virtualization on this endpoint or in the panel.

### Scan versioning and reuse

- Every `Scan` gets a per-project sequential `version` (assigned in `routers/scans.py`, backfilled for pre-existing rows by `db._run_light_migrations` since there's no alembic chain — schema changes are hand-written idempotent `ALTER TABLE` statements in `db.py`).
- `POST /scans` with no explicit `commit_sha` resolves the branch's latest commit via `git_workspace.resolve_remote_head` (no clone) and reuses an existing non-`failed` scan for that commit instead of starting a new one (`reused: true` in the response) — unless `force: true` is passed.
- `app/services/gates.py`'s `build_gate_summary` rolls a scan's `Finding` rows into severity/verdict/source counts for CI consumption; pass/fail gate thresholds were removed, so `gate_failed` is always `False` (kept only for API compatibility).

### Auth

Per-user accounts with two roles (`admin`, `user`); SQLite only for now (portable column types, no Alembic — new columns still go through `db._run_light_migrations`).

- **Who is calling** (`app/auth/principal.py` `get_principal`): `Authorization: Session <token>` is a signed-in user — an opaque token whose SHA-256 is in `user_sessions` (`app/auth/sessions.py`: 8 h idle / 12 h absolute, 14 days with remember-me; revoked on disable, password reset, own password change except the current one, and admin demotion). `Authorization: Bearer <SAST_API_TOKEN>` is the **CI service principal** with the fixed `CI_SERVICE_PERMISSIONS` scope (projects, scans incl. DAST for `tools/dast_harness`, exports; nothing admin). Errors are `{"detail": <message>, "code": <code>}` via `ApiError`.
- **What they may do** (`app/authz/catalog.py`): a code-defined catalog of `page.*` keys (sidebar/page visibility) and action keys. Admins hold everything; a user holds `user_default` keys + `grant` overrides − `deny` overrides (deny wins, table `user_permission_overrides`), never `grantable_to_user=False` keys, minus anything whose `requires` aren't all held. Evaluated from the DB on every request, so changes apply on the next click.
- **Every route must declare its auth** with `Depends(require("<key>"...))`, `require_user` or `public` — `tests/test_authz_routes.py` walks all routes (FastAPI 0.141 nests included routers as `_IncludedRouter`; use `effective_route_contexts()`) and fails on an undeclared one, and checks anonymous 401 everywhere.
- **Scan scope** (`app/authz/scope.py`): every scan sub-route goes through `authorize_scan` (via `scans._get_scan_or_404`), which answers **404** for a scan outside the caller's scope (`scans.view_all`, or `scans.view_own` + `Scan.created_by_user_id == user`); lists use `scope_scans`. CI and pre-accounts scans have no owner, so only `view_all` sees them. Reviewer/actor names (feedback, triage, DAST training reader) come from the principal, never the request body.
- **Setup and accounts**: `/setup` creates the first admin only while `users` is empty and only with `SETUP_TOKEN` (≥ 32 chars). Admins invite users (`/admin/users`); invite/reset links are single-use hashed `user_tokens` delivered as `PUBLIC_APP_URL/account/setup#t=<token>` (fragment, so it never hits server logs). Sign-in is rate-limited in memory (`app/auth/ratelimit.py`, single process); the client IP comes from `X-Client-IP` only with `X-Frontend-Key == FRONTEND_PROXY_SECRET`. `app/services/audit.py` writes `audit_events` and drops secret-looking keys.
- **Frontend**: the session token sits in an HttpOnly, SameSite=Lax cookie (`lib/session-cookie.ts`; `__Host-` + Secure in production) set only by route handlers (`app/api/auth/login`, `app/api/setup`, `app/api/auth/password`). `lib/server-sast.ts` `sastFetch` forwards it, so all ~50 proxy routes needed no change. `proxy.ts` (Next 16's middleware) redirects cookieless page loads to `/login?next=`, 401s cookieless `/api` calls, refuses cross-origin mutating `/api` calls (CSRF), and passes the path to layouts as `x-sb-path`. The root layout's `sessionForRequest()` (`lib/server-session.ts`) validates the session with the backend on full loads and renders `<Forbidden/>` for a page the user lacks (`lib/access.ts` `PAGE_ROUTES`); `AppShell` does the same on client navigation. `lib/api.ts` `apiFetch` sends a 401 to sign-in with `reason=expired`. UI hiding (`useCan`, `canStopScan`) is display only.
